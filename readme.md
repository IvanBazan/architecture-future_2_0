## Задание 1. Архитектура системы для «Будущего 2.0» через год

Текущее состояние:
- все корпоративные данные в DWH (SQL Server). В нём была реализована значительная часть бизнес-логики, а для работы операторов в клиниках использовался интерфейс на PowerBuilder
- стек:
  - DWH (Microsoft SQL-сервера 2008 года)
  - Power BI
  - Power Builder
  - Шина на базе Apache Camel
  - ИИ-сервисы на Python
  - Финтех-сервисы на Golang и Java

Проблемы:
- очень большой объем данных (сотни ТБ)
- много сценариев использования данных -> много трансформаций
- формирование сложных отчётов может занимать часы -> падает TtM, страдает аналитика   

Бизнес Планы:

- интегрировать в экосистему нескольких фармацевтических компаний и производителя электроники для медицинского оборудования
- развивать каждое из своих направлений отдельно, сохраняя при этом целостное представление по ключевым бизнес-показателям

Технические планы:

- перенос основной части IT-ландшафта в облачную инфраструктуру
- В облаке предполагается выстраивать отдельные среды для разных доменов, чтобы обеспечить их независимость и упростить развитие
- Для критичных систем будут использоваться механизмы отказоустойчивости, резервного копирования и геораспределённого развёртывания
- ключевая задача - обеспечение информационной безопасности и соблюдение требований регуляторов, особенно в части работы с медицинскими и финансовыми данными

Требования:

- Создать «витрину данных»:
  - легкая масштабиуемость
  - сотрудник сможет получить в этой системе отчёт по любым необходимым срезам в пределах своего уровня доступа
  - сотрудник может конструировать собственные отчеты
  - в «витрину данных» не будут включаться медицинские карты, истории болезней и результаты медицинских исследований
- архитектурное решение по изменению IТ-ландшафта в области работы с данными
  - интеграцию новых бизнес-направлений без необходимости вносить значительные объёмы бизнес-логики в DWH

Предстоящие изменения:

##### Разбиение данных лежащих на данный момент в одной БД на домены:
1. *Медицинский* (пациенты, медкарты, истории болезней)

Данные требующие особо тщательной сохранности. Компрометация моет привести к нарушению 152 ФЗ. 
Необходима тщательная настройка контролей доступа.
Основные пользователи:
  - Операторы в клиниках
  - Разработчики ИИ сервисов

Предлагаю создать отдельное хранилище БД + s3 с настройкой RBAC:
Структурированные данные переносим как есть в новю базу
BLOB данные, которые судя по всему также хранились в SQL server лучше выносить в S3 


Если на первом этапе хотим сохранить функциональность существующего PowerBuilder клиента, то необходимо реализовать API Gateway и rest сервис для работы с S3. 

Возможно имеет смысл оставить некоторую интеграцию БД с шиной данных для сохранени возможности получения общей информации по пациентам (без специальной медицинской) остальными аналитическими системами

Для команды ИИ разработки вероятно данные должны проходить обезличивание. Значит у данного кластера данных вероятно будет два контура, контур с "настоящими" чистыми данными и данными прошедшими обработку (маскирование, обезличивание и тд). К тому же предлагаю ИИ сервисам теперь напрямую ходить на обработанный контур не давая нагрузки на шины 

2. *Финтех* (финансовые операции, банкинг)

Домен финансовых операций самый чувствительный к проблемам работоспособности системы. Любые неполадки в работе и уменьшение производительности системы напрямую влияют на репутационные и финансовые показатели.

Первоочередная задача избавить финансовую систему от необходимости взаимодействия с перегруженными аналитикой компонентами.

Так как события финансовой системы требуются в отчетах и аналитике, то предлагается транслировать их через брокер сообщений например Kafka.
Таким образом сама финтех система не будет нагружаться и будет независимой от остальных операций в системе, но данные будет возможно использовать в витрине.

Также данная система вероятно должна иметь Апи для взаимодействия с ней например Медицинской системой (для администрирования финансовых операций пациентов операторами в клиниках)

3. *Административные данные*

Данные с которыми работают сотрудники управления компании.
Я не вижу прямой причины для того чтобы выносить эти данные из существующей базы. Вероятно из необходимых работ, это проверка настроек контролей доступа, так как раньше DWH использовался всеми системами, а сейчас мы оставляем только административную и аналитическую 

##### Реализация универсальной витрины данных:

После разбиения на домены мы получили несколько разрозненных источников данных необходимых для витрины.

Предлагаю старую систему отчетов через PowerBi + DWH продолжать поддерживать, пока она не потеряет ценность.
Параллельно с этим переводить PowerBi на новый источник данных в витрине

Для реализации витрины будет необходимо поднять Apache Airflow, который будет отвечать за перекачку данных из доменных баз и старого DWH в новое хранилище
Для универсальности создаваемых отчетов придется грузить максимально необработанные данные.
Так что будем использовать как s3 хранилища так и Postgre или Snowflake для структурированнных

### Проблемные места текущей системы

1. Все процессы компании завязаны на одну DWH бд
   1. DWH является точкой отказа
   2. Увеличение пользователей и сервисов в системе будет приводить к необходимости удовлетворять экспоненциальный рост затрат на вертикальное масштабирование мощностей базы
   3. Слабо связанные операции из потенциально разных доменов грузят одну точку с совершенно разными профилями нагрузки
   
2. В системе много данных требующих защиты и шифрования
   1. настройку контролей доступа внутри одной системы труднее настраивать и поддерживать

3. Любое подключение новых систем сопряжено с необходимостью соблюдать правила и ограничения текущего DWH монолита

4. текущая DWH база используется фактически в двух режимах и как OLAP и OLTP 
   1. страдает бизнес аналитика так как система не может оперативно работать с данными, что приводит к ухудшению принятия решений
   2. перегрузка системы тяжелыми аналитическими запросами может влиять на быстродействие ситемы в части транзакционных операций, что может привести к негативному опыту работы например с финансовыми операциями, что крайне негативно повлияет на пользовательский опыт
   3. сложно развивать систему сразу по двум направлениям
